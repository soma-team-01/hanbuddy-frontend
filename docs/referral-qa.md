# 제휴 활동 연동 확인 — #176

## 범위

HanBuddy에서는 신청·취소·개인정보 제공 동의·신청 건수만 관리한다. 실제 서비스 요금과 예약은 업체 상담 후 별도로 확정한다. 건당 수수료 계산, 청구, 정산, 외부 예약 완료 상태는 이번 구현에 포함하지 않는다.

## 실제 서버 확인 전 준비

- 실행 중인 서버의 OpenAPI에서 `MyActivityDetailResponse.activityType`과 `PATCH /referral/activities/{activityId}`가 모두 존재하는지 확인한다. 2026-10-02 재점검 당시 localhost:8080은 두 항목이 없는 이전 계약으로 응답했다. 소스에 코드가 있어도 실행 중인 서버가 이전 빌드이면 제휴 편집·가격 분기가 동작하지 않는다.
- 유형이 누락되거나 알 수 없는 값이면 편집 화면은 오류를 표시하고 저장 폼을 열지 않는다. 가격이 0이라는 이유만으로 제휴 유형을 추정하지 않는다. 정상 `REFERRAL` 응답에서는 0원을 `무료`로 표시하고 전용 PATCH에 `price: 0`을 전달한다.
- 같은 날 사용자 재실행 후 위 두 계약과 `ReferralActivityRequest.price >= 0`을 다시 확인했다. 실제 공개 응답의 활동 7·8은 `REFERRAL / price: 0`, 활동 2·3은 `STANDARD`로 정상 분리되었다. 실제 활동 수정·신청 데이터는 변경하지 않았으며, 저장 동작은 격리 fixture에서 확인한다.
- 백엔드 `feat/#193-referral-activity-applications` 최신 코드와 V60/V61/V62가 적용된 로컬 DB를 준비한다. Swagger의 `ReferralActivityRequest`에 필수 `price`, 신청 요청에 `reapplyFromApplicationId`가 있는지 확인한다. 운영 DB를 테스트에 사용하지 않는다.
- 프론트의 `HANBUDDY_API_BASE_URL`을 해당 로컬 백엔드에 연결한다.
- 관리자, 활성 버디 A/B, 여행자 계정을 준비한다. 버디 B는 타 업체 접근 차단 확인용이다.
- 등록할 회차는 한국 시간 기준 시작까지 24시간 이상 남기고 정원을 작게 설정한다.
- 이 문서의 `/ko`는 한국어 경로다. 여행자 화면은 `/en`, `/ja`, `/zh-Hans`, `/zh-Hant`로도 확인한다. 버디·관리자는 기존 한국어 운영 화면을 따른다.

### 오류·회귀 확인

- 제휴 활동 상세·미리보기의 항목은 `10분`처럼 시간만 표시하고 상품 번호·단계는 붙이지 않는다. 일반 활동의 단계 표시는 유지한다(5개 언어). 버디 활동 등록·수정 헤더는 언어 버튼 없이 나가기만 표시하며 임시 저장·새로고침 복원은 유지한다.

- 목록 상단의 중복 제휴 활동 제목은 표시하지 않는다. 등록 링크 만들기 버튼은 목록에만 있고 신청 현황에는 없다.
- 상단 인원은 취소하지 않은 모든 페이지의 `guestCount` 합계이며 고유 사용자 수가 아니다. 한 신청으로 3명을 예약하면 인원 3명·신청 1건이다. 아래에는 신청자, 활동 일시·인원, 연락처, 신청 일시·상태를 신청별 카드로 표시한다.
- 기간 달력의 점은 선택 활동에 신청된 `createdAt`의 한국 날짜 기준이며 취소 건도 포함한다. 표시 월의 모든 페이지를 조회하고 날짜만 보관한다. 활동 시작일을 사용하지 않으며 점 없는 날짜도 선택할 수 있다. 양 끝 날짜 포함, 같은 날, 월을 가로지르는 선택, 전체 기간 초기화, Escape 취소와 포커스 복귀를 확인한다. 표시 조회 실패는 별도 안내하고 기간 선택은 막지 않는다.

- 활동 통합 검색은 비활성 버디도 포함해 3개 필드의 모든 검색 페이지를 합친 뒤 활동 소유자 ID로 연결한다. 기존 API에 활동 키워드·복수 신청 상태 필터가 없어 전체 관련 페이지를 확인한다. 취소 제외 내역은 CONFIRMED+COMPLETED를 합산하며 일부 페이지 실패 시 불완전한 결과를 표시하지 않는다. 데이터가 커지면 해당 필터를 백엔드 페이지 조회에 추가하는 것이 권장된다.
- 발급 내역은 업체를 선택한 뒤에만 표시한다. 업체를 바꾸면 해당 계정의 내역으로 교체하고, 새 검색 시 다시 숨긴다. 링크 발급·회수 후 내역이 갱신되는지 확인한다. 현재 목록 API에는 업체별 필터가 없어 모든 페이지를 확인한 뒤 선택한 `buddyId`만 보관·표시한다. 서버 필터가 추가되면 업체별 서버 페이지 조회로 교체할 수 있다.
- 등록 링크의 업체 검색 결과는 기존 관리자 상세 API로 전체 이메일을 확인한다. 닉네임이 같은 계정도 이메일로 구분할 수 있어야 한다. 조회 실패 시 계정 선택을 막고 이메일 재조회를 제공한다. 전체 상세 응답을 캐시하지 않고 이메일만 보관하며, 검색 결과가 사라지면 해당 캐시도 제거한다.
- 만석·24시간 마감·시간 중복·비공개 활동은 서버 오류를 안내하고 신청을 성공 처리하지 않는다.
- 최신 동의 버전이 달라지면 안내를 새로 조회하고 체크를 다시 받아야 한다.
- 빠르게 두 번 눌러도 발급·신청·취소가 중복 요청되지 않아야 한다.
- 재신청 화면은 `/applications/me`를 새로 확인한다. 같은 활동·회차의 유효한 신청이 있거나 버디가 회차를 취소했으면 제출을 막는다. 취소 이력이 있으면 가장 큰 `applicationId`를 최신 취소 ID로 사용하며, 최초 신청은 `reapplyFromApplicationId`를 생략한다.
- 취소한 회차는 `재신청하기` 버튼과 새 신청 생성 안내를 표시한다. 동의는 미체크 상태이고 회차·취소 ID·동의 버전이 바뀌면 이전 동의를 재사용하지 않는다. 사용자가 직접 동의하고 버튼을 눌렀을 때만 최신 취소 ID를 POST body로 보낸다. 다른 회차를 고르면 이전 회차 ID를 보내지 않는다.
- `APPLICATION409_REFERRAL_EXISTS` 또는 `APPLICATION409_REFERRAL_REAPPLICATION`은 신청 목록·동의 안내를 새로 조회하고 체크를 해제한다. 최신 ID를 자동으로 넣어 POST를 재시도하지 않는다. 목록 조회 실패 시에도 제출을 막고 재조회 버튼을 표시한다.
- 재신청 성공은 새 신청 ID를 사용하고 기존 취소 기록은 유지한다. 만석·24시간 마감·시간 충돌·비공개/취소 회차는 서버가 최종 판단하며, 오류 응답에 확정 화면을 표시하지 않는다. 비정상적으로 `CANCELLED`가 반환된 경우도 확정 처리하지 않는다.
- #193/V62 소스 계약을 기준으로 연결했다. 2026-10-02 실행 중인 localhost:8080의 OpenAPI를 확인했으나 `reapplyFromApplicationId`가 없고 취소 여부와 무관하게 기존 신청을 반환하는 이전 계약이었다. 실제 DB 재신청 검증은 V62 적용 및 최신 서버 준비 후 필요하다. 앱 DB 마이그레이션·서버 재시작은 프론트 작업에서 수행하지 않는다.
- 일반 `STANDARD` 활동은 기존 등록·가격·결제·취소·환불 흐름을 그대로 유지한다.
- 일반·제휴 등록/수정의 데스크톱 뒤로가기 화살표는 제목 위 별도 줄에 표시한다. 모바일·태블릿에서는 상단 화살표를 숨기고 하단 이전/다음 버튼으로 이동한다. 첫 단계의 이전 버튼은 비활성화하고, 이전/다음 왕복 시 입력 내용을 유지한다. 수정 화면의 바로 저장 버튼도 유지한다.
- 일반·제휴 등록/수정의 일정 단계는 날짜 아래 작은 ×로 선택 날짜를 삭제한다. 현재 편집 날짜만 진한 빨강, 나머지 선택 날짜는 흰 배경에 빨간 테두리로 표시한다. 시간이 하나 이상 설정된 날짜에만 아래 점을 표시하고 마지막 시간을 해제하면 점도 사라진다. 날짜에는 연한 빨강 배경을 사용하지 않는다. 달력 배경, 별도 날짜 문구, 선택 방법·KST·24시간 마감 안내는 화면에서 제거하되 시간대와 마감 동작은 유지한다. 오전·오후 30분 간격 버튼은 그대로 두고, 오전/오후 토글 + 시(1–12)·분(0–59) 직접 입력으로 추가한 비정규 시간은 아래에 '오전 08:10 ×' 카드로 표시한다. '해당 시간 일괄 적용'을 체크하면 이후 시간 변경과 새 날짜 선택에도 동일한 시간이 반영된다. 체크 해제 후에는 날짜별로 독립 편집되며, 마지막 시간 해제·중복 입력·오전/오후 12시·한국 시간 기준 지난 시각 차단도 확인한다. 시간 목록 내부 스크롤 없이 추가 카드가 많으면 본문이 자연스럽게 늘어난다.
- 초대 코드가 API query/path, 분석 이벤트, 오류 로그에 포함되지 않는지 확인한다. 검증/등록에 필요한 POST body로만 전달한다.
- 여행자 UI 문구는 5개 언어를 지원한다. `referral-notice`의 서비스 안내·목적은 동의 계약을 보존하기 위해 서버가 반환한 원문 그대로 표시한다. 제공 항목 중 알려진 필드 키(name/contactMethod/contactCountryCode/contactIdentifier)는 각 언어의 이름·연락 수단·국가 전화번호·연락처로 표시하고, 그 외 값은 원문을 유지한다.
- 제휴 신청 화면은 일반 예약과 같은 날짜 달력·인원 ± 버튼 및 데스크톱 2열 요약 패널을 사용한다. 모바일에서는 요약을 아래 박스로 배치하고 개인정보 제공 동의·신청 버튼을 하단에 고정한다. 날짜 변경 시 정원이 줄면 인원을 조정하며 신청 정보가 즉시 갱신된다. 서비스 최소 금액은 인원에 곱하지 않고, 결제 합계·환불 정책·PG 버튼은 표시하지 않는다. 특별 요청은 버디에게 전할 말 입력으로 제공하며 `specialRequest` 계약을 사용한다. 동의 버전 변경·중복 제출 차단은 유지한다.

- 최종 전체 검증: 포맷·ESLint·TypeScript·269개 테스트 파일/2,512개 테스트·프로덕션 빌드 통과. 일반·제휴 신청 완료 화면은 공통 UI를 사용하고 모바일 버튼을 고정 바 대신 본문에 포함한다. 한·영 390/768/1024/1440px에서 줄바꿈·가로 넘침·링크·키보드 이동을 확인했다.
- 모바일 푸터는 약관·언어/연락처·사업자 정보·저작권 순서로 정리하고 정보와 링크를 유지한다. 5개 언어 × 320/390/768/1024/1440px에서 가로 넘침, 언어 메뉴 열기/닫기와 포커스 복귀를 확인했다. 768px 이상은 변경 전 레이아웃과 동일하며, 390px 높이는 306px에서 언어별 약 213~245px로 줄었다.
